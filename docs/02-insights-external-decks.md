## Часть A. Для проекта Smart University

### Приоритет 1 — двигают качество и защиту прямо сейчас

**1. [ADD → в v1.1] RAG-триада как раздельные гейты — §12.**
Было `faithfulness` + `context_recall`. Триада требует три ребра «Запрос→Контекст→Ответ»:
- **context_precision / relevance** — доля релевантных предложений в контексте (не то же, что recall: recall = «достали ли всё», precision = «сколько мусора»). Диагностирует retrieval.
- **answer_relevancy** — ловит «ответ обоснован по контексту, но не на заданный вопрос». Критично для узких вопросов абитуриентов.
> `faithfulness` и `answer_relevancy` независимы — меряем обе оси, иначе уклончивые ответы пройдут гейт.

**2. [ADD → в v1.1] Судья ≠ генератор — §12, §2.5.**
Если Ragas-судья тоже GPT, а генерируем `gpt-4o-mini` — self-preference bias завышает оценки. Судья из другого семейства (модель другого вендора/локальная) хотя бы для faithfulness. Провайдеро-агностичный слой это уже позволяет — зафиксировать отдельную `judge_model` в конфиге.

**3. [REFINE → в v1.1] Deploy-time hard-gate ≠ runtime confidence gate — §9, §14, §15.**
У нас есть runtime `pre-LLM confidence gate` (на каждый живой запрос). Нужен ОТДЕЛЬНЫЙ **deploy-time hard-gate**: релиз промпта/модели/переиндексации блокируется, если на golden-наборе метрики ниже порога. Это два разных механизма — нужны оба. Кейс Roima со слайдов: «ручное ревью → релизы без страха».

**4. [ADD → в v1.1] Data drift и свежесть контента — §7, §17 (риск 16).**
Инвариант §2.10 версионирует индекс под **модель эмбеддингов**, но не под **свежесть контента**. В вузе правила приёма/расписания/стоимость меняются каждый семестр, старые чанки живут в Qdrant. Действия: `doc_version`/`fetch_timestamp` в метаданных (уже есть в §6.1) + стратегия **переиндексации per-tenant** при обновлении источника + метрика свежести на дашборде.

**5. [CONFIRM] Grounding-only + цитаты из source_nodes — §2, §9, §11.**
Оба дека механистически обосновывают наши инварианты: LLM предсказывает токен, а не извлекает факт → отсюда галлюцинации несуществующих ID/ссылок. Усилить в защите. **Проверить: цитата вешается на КАЖДОЕ фактическое утверждение (claim-level), а не общим списком внизу** — тогда faithfulness проверяем, а галлюцинация операциональна: «утверждение без линии к контексту».

**6. [CONFIRM] Reranker + top-k отсечение против attention dilution — §8.**
«Больше контекста ≠ лучше»: шум размывает attention и растит галлюцинации. Наш `bge-reranker-v2-m3` + `top_k=5` — прямая реализация. **Проверить: после reranking мы реально ОТСЕКАЕМ низкоскоринговые чанки (порог/жёсткий top-k), а не только переупорядочиваем.** Не раздувать k «на всякий случай».

**7. [CONFIRM → в v1.1] cosine — только для retrieval, НЕ для оценки ответа — §8 vs §12.**
Слайд 3 хоронит BLEU/ROUGE/cosine как метрики КАЧЕСТВА ОТВЕТА. Мы правы (Ragas = LLM-judge). В защите проговорить: cosine у нас = dense-retrieval (§8), качество ответа = Ragas (§12). Не путать.

### Приоритет 2 — операционная зрелость и экономика

**8. [ADD → в v1.1] Online-контур обнаружения галлюцинаций — §12 (риск 17).**
«Незамеченные» галлюцинации доходят до пользователя, минуя CI. Online-eval: сэмплинг faithfulness/relevance на живых логах Langfuse (~5% случайных + ВСЕ кейсы со сработавшим gate/низким rerank) → флаг «нет источника/низкая faithfulness» → ручной разбор. Langfuse + кастомные RAG-Triad-скореры покрывают роль TruLens — не плодить инструменты.

**9. [ADD → в v1.1] Каскад оценки — экономика LLM-as-a-Judge — §12.**
Не судить 100% трафика флагманом. Воронка: **L1** детерминированные эвристики (есть `source_nodes`? цитаты? сработал gate?) → **L2** дешёвый сигнал (низкий rerank-score `bge-reranker-v2-m3` = плохой контекст) → **L3** дорогой LLM-судья только на <1–5%. Reranker уже в стеке — бесплатная eval-эвристика.

**10. [ADD → в v1.1] Semantic cache первым слоем — §5, ADR-011 (риск 19).**
У приёмной комиссии доля повторяющихся вопросов огромна. Кэш по эмбеддингу (BGE-M3 уже есть), ключ = `f(tenant_id, semantic_hash)` — **обязательно с `tenant_id`, иначе утечка между тенантами**. Режет стоимость генерации, стоимость оценки и латентность.

**11. [ADD → в v1.1] Cost/latency как first-class метрики — §12, §14 (риск 18).**
Токены in/out и cost **per-tenant/per-query** в Langfuse. Trace-waterfall по шагам: BGE-M3 → Qdrant(hybrid+RRF) → reranker → gpt-4o-mini (мерить и лишний шаг reranker). Пик подачи документов = бюджетный риск.

**12. [ADD] Synthetic golden-set per-tenant с эволюцией сложности — §12.**
Ragas `TestsetGenerator` из корпуса KBTU вместо только ручных тестов. **Отдельный набор на каждый `tenant_id`** (приёмка vs студофис vs факультеты), иначе средняя метрика замаскирует деградацию одного тенанта. Три типа мутаций: **reasoning / multi-context / conditional** — вскрывают дыры чанкинга и retrieval (условия поступления, сроки, исключения). Провалы из прода → новые кейсы.

### Приоритет 3 — структура retrieval и защита выбора

**13. [CONFIRM] Qdrant + HNSW + hybrid dense+BM25+RRF = мейнстрим — §5, §6, §8.**
Qdrant назван лидером наравне с Milvus/Pinecone/pgvector — выбор не нишевый. BM25 в RRF подтверждён: dense ловит перефраз, BM25 — точные токены (коды дисциплин, номера приказов, аббревиатуры). В защите ссылаться на консенсус.

**14. [REFINE] Осознанно затюнить и задокументировать HNSW — §8, §14.**
HNSW приближённый (recall < 100%), зависит от `m / ef_construct / ef_search`. Зафиксировать значения в конфиге и хотя бы раз сравнить ANN с exact-поиском на golden-set, чтобы измерить реальную потерю recall. Частый вопрос на защите про latency/recall trade-off.

**15. [REFINE] Structure-aware чанкинг сохраняет иерархию/причинность — §7.**
Наивное фиксированное окно рвёт заголовки и причинно-следственные связи → бьёт по процедурным вопросам («что если не сдать документы к дедлайну»). Убедиться, что `HybridChunker` (700 ток) держит heading-структуру. Инструмент уже правильный — подтвердить настройку.

**16. [REFINE] Payload-метаданные для точных предикатов — §6.**
SQL-парадигма сильна там, где вектор слаб: точные фильтры по дате/ID/коду. Структурированные атрибуты (дедлайны, стоимость, коды специальностей) хранить как payload-метаданные Qdrant для точной фильтрации, не полагаясь на dense. Наш `tenant_id`-фильтр — уже пример; расширить на бизнес-атрибуты.

**17. [CONFLICT/нюанс → в v1.1] Плоский top-k проваливает multi-hop и суммаризацию — §17 (риск 15), ADR-012.**
Оба дека сходятся: чистый top-k структурно НЕ умеет (а) multi-hop reasoning, (б) суммаризацию корпуса, (в) сохранение иерархии/причинности. Рекомендация:
- **Не мигрировать на GraphRAG в MVP** — для FAQ приёмки основной поток это «local» факт-вопросы, где hybrid+reranker оптимален по точности/латентности/цене.
- **Честно задокументировать** как известное ограничение MVP (сделано, риск 15), а не маскировать под фичу.
- Добавить в eval отдельную категорию **multi-hop / global-summary** (сделано, §12).
- **Community Summaries переносимы БЕЗ полного графа**: offline-предгенерация тематических per-tenant резюме (по программе/факультету/типу документа) как отдельные summary-ноды в той же Qdrant-коллекции с `tenant_id` — «обзорные» вопросы отвечаются из резюме, дёшево и совместимо с guardrails (резюме = цитируемый source_node). Дешёвый вход в rich-mode.

**18. [ADD] Query routing по классу интента — §8, §10.**
Классифицировать запрос: точный факт / семантический / multi-hop / суммаризация — и по-разному строить контекст. Минимум — отдельный маршрут для агрегирующих запросов (предфильтр по метаданным + map-reduce), а не только top-k similarity.

### Про дек AI-memory — заложить в будущий чат-ассистент (НЕ переусложнять MVP) — ADR-013

Слайд 14 вводит **Agentic Memory**. Для будущего диалогового слоя заложить архитектурное место (изолированное **per-tenant И per-user**), но не строить в MVP:

- **Два слоя памяти, а не плоский лог:** (1) векторная семантическая память прошлых реплик (recall); (2) структурированная/графовая память сущностей пользователя (заявки, статусы, ранее заданные вопросы).
- **Типы памяти:** **working** (текущий диалог), **episodic** (прошлые сессии), **semantic** (устойчивые факты о пользователе/предметке), **procedural** (как ассистент выполняет типовые сценарии).
- **Суммаризация памяти:** длинные диалоги сжимать в резюме (тот же приём Community Summaries).
- **Memory retrieval:** доставать релевантные фрагменты памяти через retrieval, а не грузить весь лог.
- **RBAC-гранулярность:** доступ per-сущность/владелец — персональные данные студента изолированы от общего справочного слоя. Для MVP достаточно `tenant_id`, но модель заложить.

**MVP-позиция:** чат-память откладываем, но проектируем интерфейсы так, чтобы добавить слой памяти без переписывания retrieval.

### Нарратив для питча/защиты — §1, README

- **Метафора айсберга:** «10% — демо на поверхности (retrieval + LLM = 10 строк), 90% инженерии под водой». Открывать питч этим — объясняет нетехническому руководству вуза, почему «просто прикрутить ChatGPT» ≠ продукт.
- **Три проблемы голой LLM → наш стек как ответ:** knowledge cutoff / hallucinations / нет private-data контекста. Каждой проблеме — конкретный компонент. Архитектура становится аргументом.
- **Одна фраза про RAG:** «модель не вспоминает факты из обучения — она читает их из вашей базы в момент запроса». Обоснование RAG вместо fine-tune для README.
- **Рамка:** «RAG — не векторный поиск, а инженерная дисциплина непрерывной оценки» (метрики + инструменты + CI/CD как обязательная часть архитектуры).

## Часть B. Durable-принципы (переиспользуемо, вне KBTU)

Сохранены в проектную память (reference: `reference-rag-production-playbook`, `reference-agent-memory-design`). Дублируются здесь для самодостаточности репозитория.

1. **Оценивай RAG триадой, а не одной цифрой:** Context Relevance (retrieval), Faithfulness (генерация опирается на контекст), Answer Relevance (ответ на заданный вопрос). Одна метрика скрывает, КАКОЙ слой сломался.
2. **Faithfulness и Answer Relevance независимы:** ответ может быть на 100% обоснован и не отвечать на вопрос. Меряй обе оси.
3. **Разделяй роли cosine similarity:** в retrieval легитимен, как метрика КАЧЕСТВА ответа вводит в заблуждение. BLEU/ROUGE/строковый match мертвы для свободной генерации → LLM-as-a-judge.
4. **Судья ≠ генератор (self-preference bias):** не давай модели оценивать саму себя. Судья — из другого семейства и всегда с контекстом на входе.
5. **Больше контекста ≠ лучше:** нерелевантные фрагменты размывают attention и растят галлюцинации. Оптимизируй плотность сигнала (rerank + отсечение), а не объём.
6. **Определяй галлюцинацию операционально:** «утверждение, не выводимое из контекста», а не «фактически неверно». Считай faithfulness на уровне атомарных claim'ов.
7. **Две обязательные среды оценки:** offline regression-gate до релиза (Ragas на замороженном golden-set) + online-observability на живом трафике (Langfuse). Offline не покрывает дрейф.
8. **Eval — исполняемый hard-gate в CI/CD, а не лог:** релиз блокируется автоматически. Различай deploy-time gate и runtime guard — разные механизмы, нужны оба.
9. **Register из 4 production-рисков с первого дня:** (1) деградация промптов при масштабе, (2) data/embedding drift, (3) необнаруженные галлюцинации на живом трафике, (4) рост стоимости API. Cost/токены — метрика observability с первого дня.
10. **LLM-as-a-Judge каскадом, не флагманом на 100%:** semantic cache → эвристики → малая/локальная модель → дорогой LLM на <1–5%. Дешёвый быстрый слой перед дорогим.
11. **Гибрид dense+BM25+RRF почти всегда бьёт одиночный ретривер:** dense — перефраз, BM25 — точные токены. ANN приближённый — измерь потерю recall vs exact. Точные предикаты (id/дата/tenant) — на структурированном слое.
12. **Знай пределы плоского top-k:** не умеет multi-hop, суммаризацию корпуса, иерархию. Тестируй эти классы явно. GraphRAG — другой класс задач, не «лучше». Community Summaries переносимы без полного графа.
13. **Память агента — отдельная архитектура, а не лог диалога:** векторная семантическая + структурная/графовая. Типы: working/episodic/semantic/procedural. Длинные диалоги суммаризируй; память доставай через retrieval.
14. **Безопасность в мультитенантных системах — гранулярная, с первого дня:** `tenant_id` на КАЖДОМ слое (векторы, граф, summary, кэш, память); доступ вплоть до per-сущность/владелец. Ретрофитить изоляцию дороже.
15. **Сохраняй структуру документа при чанкинге:** heading-aware вместо наивного окна. Для мультитенантных eval — отдельный golden-set на домен/тенант, с эволюцией сложности (reasoning/multi-context/conditional).
16. **Продавай RAG нарративом:** три проблемы голой LLM → компонент под каждую; «модель не вспоминает, а читает из базы»; «10% демо, 90% инженерии». Связка «проблема ↔ компонент» превращает архитектуру в защиту.

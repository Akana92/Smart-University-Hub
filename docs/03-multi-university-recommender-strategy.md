# Стратегия расширения — Мультивузовская платформа + Рекомендательный движок грантов

> **Статус:** стратегическое расширение фундамента (`docs/00-foundation.md`; актуальную версию см. в его шапке — на 2026-07-03 это v1.4). Этот документ **не отменяет** §00, а надстраивает над ним второй продукт-контур. Все инварианты §2 (`tenant_id`-фильтр, цитаты из метаданных, единый code path к вектор-стору, анти-галлюцинация) остаются в силе и **распространяются на новый структурный движок**.
>
> **Одна фраза:** мы превращаем «RAG-ассистента одного вуза» в **двустороннюю платформу поступления в вузы РК**: абитуриент вводит балл ЕНТ + профильные предметы и получает честный, объяснимый расклад «куда пройду на грант / куда платно / что делать дальше»; вузы приносят свою документацию и платят за присутствие и лиды.

## 1. Продукт и позиционирование

### 1.1. Что строим

**Двусторонняя платформа (two-sided marketplace) вокруг поступления в вузы Казахстана.**

Две стороны, две ценности:

| Сторона | Кто | Что получает | За что платит / чем платит |
|---|---|---|---|
| **Спрос** | Абитуриент + родитель | (1) Ответы по документам конкретного вуза (RAG, §00). (2) Рекомендация «куда пройду на грант» по баллу ЕНТ + профильным предметам, с источником и годом. (3) Дерево сценариев «если не хватает баллов». | Бесплатно (публичные данные). Платит **вниманием и данными о спросе**. |
| **Предложение** | Вуз (приёмная комиссия, маркетинг, проректор по акакдемвопросам/развитию) | Присутствие в поиске абитуриентов, входящие лиды, аналитика спроса, self-serve загрузка своих документов в RAG-ассистента. | Деньгами (подписка / pay-per-lead / спонсорское размещение). |

Ядро — **два разделённых движка** (детально в §4):

- **Движок A — RAG** (vector/hybrid, ровно как в §00): «Можно ли пересдать FX?», «Какие документы нужны для поступления?», «Сколько стоит IT в KBTU?» — ответы из документов вуза с цитатами.
- **Движок B — Рекомендатель** (структурированный стор + правила): «Мой балл 92, профиль математика+информатика — куда пройду на грант?» — расчёт по историческим отсечкам с явной ссылкой на источник и год.

### 1.2. Для кого

1. **Первичный ЛПР спроса — абитуриент 11 класса / выпускник колледжа** (17-19 лет), плюс **родитель** (реальный ЛПР по деньгам и «куда нести документы»). Момент максимальной боли — июнь-август: результаты ЕНТ известны, до подачи заявления на конкурс дни, цена ошибки в расстановке 4 приоритетов = потерянный грант.
2. **Вторичный ЛПР спроса — школьный профориентатор / репетиторский центр** (готовит абитуриента, нуждается в инструменте-калькуляторе).
3. **ЛПР предложения** — см. §6.4.

### 1.3. Чем отличаемся от конкурентов и какие пробелы закрываем

Рынок агрегаторов баллов в РК **существует** (univision.kz, studenthub.kz, abiturients.kz), но у всех одна и та же структурная слабость, из которой растёт наше отличие:

| Что делают конкуренты (univision, studenthub) | Пробел | Что делаем мы |
|---|---|---|
| Публикуют таблицы проходных баллов по вузам/ГОП | **Не разделяют пороговый и проходной балл явно** → абитуриент путает «допуск» с «поступлением» | Жёстко разводим два поля `threshold` vs `passing` в данных и в UX (§2). Это наш главный содержательный дифференциатор. |
| Показывают число как факт текущего года | **Выдают историческую отсечку как гарантию** | Показываем историческую отсечку **как вероятность с интервалом [min..max] по годам + источник + год**, никогда как гарантию (§2, §5). |
| Дают балл, но не логику конкурса | **Не моделируют механику 4 приоритетов** (система даёт грант по первому проходящему приоритету) | Симулируем расстановку приоритетов: «смешай амбициозные и запасные», предупреждаем о риске «4 недостижимых выбора → сильный абитуриент без гранта» (§5). |
| Только баллы, отдельно от документов вуза | **Нет ассистента по документам** конкретного вуза | RAG-движок А отвечает по регламентам/стоимости/срокам с цитатами — единый продукт «балл + документы». |
| Данные «носят ознакомительный характер» (сами так пишут), провенанс не показан | **Нет провенанса и честности о неопределённости** | Каждая цифра несёт `source_url + year + granularity + confidence`; неопределённость — часть UX, а не мелкий шрифт. |
| — | **Никто не закрывает сценарий «баллов не хватило»** структурированным деревом | Дерево решений: пересдача → платное с переводом → гранты акиматов → колледж (пороги 25/35) → автономные вузы → следующий год (§5). |

**Позиционирование одной строкой:** «Единственный ассистент поступления в РК, который честно объясняет разницу между *допуском* и *поступлением*, показывает шансы с источником и годом, и ведёт за руку, даже если баллов не хватило».

Мы **не** конкурируем «у кого таблица баллов больше». Мы конкурируем **доверием, объяснимостью и полнотой сценария** — тем, что защищаемо и продаваемо (совпадает с целью проекта: «defendable & sellable»).

## 2. Реальность данных о баллах (честно)

Этот раздел — **источник истины по предметной области**. Любая фича рекомендателя обязана ему соответствовать. Ошибка здесь = юридический и репутационный риск.

### 2.1. Как устроен грант-конкурс (механика, которую обязан знать движок)

1. Абитуриент сдаёт **ЕНТ**: максимум **140 баллов**, 5 предметов = 3 обязательных (История Казахстана, математическая грамотность, грамотность чтения) + **2 профильных**, привязанных к специальности.
2. Должен преодолеть **ПОРОГОВЫЙ балл** — фиксированный законом минимум для **допуска к конкурсу**.
3. Участвует в **едином национальном конкурсе**, указывая **до 4 приоритетов** «группа образовательных программ (ГОП) + вуз», ранжированных по желанию. Профильные предметы во всех 4 выборах **должны совпадать**.
4. Система присуждает грант **по первому приоритету, где балла хватило**; при недоборе спускается ко 2-му, 3-му, 4-му.
5. **ПРОХОДНОЙ балл** формируется **постфактум** как балл последнего зачисленного грантника по данной ГОП (+ вузу для топ-вузов).

> **Критично для модели данных:** конкурс идёт **по ГРУППАМ образовательных программ (ГОП: напр. B001 Педагогика, B049 Право, B057 ИТ, BM086 Медицина)**, а не по отдельным специальностям. ⚠️ Коды ГОП в этом документе **иллюстративны** (источники расходятся в написании, напр. B086 vs BM086) — **канонический список кодов берём из классификатора adilet при загрузке данных**, а не хардкодим. Специальность выбирается **внутри ГОП после зачисления**. Значит «проходной балл по конкретной специальности» на этапе гранта **строго не существует** — только по ГОП. Это нужно проговорить в UX (см. §7, риск гранулярности).

### 2.2. ПОРОГОВЫЙ vs ПРОХОДНОЙ — разграничение, на котором стоит весь продукт

| | **ПОРОГОВЫЙ балл** (threshold) | **ПРОХОДНОЙ балл** (passing / competitive cutoff) |
|---|---|---|
| Смысл | Минимум для **допуска** к конкурсу | Балл **последнего зачисленного** грантника по ГОП |
| Когда известен | **ЗАРАНЕЕ**, стабилен | **ТОЛЬКО ПОСТФАКТУМ**, плавает год к году |
| Кто задаёт | Закон / приказ МНВО | Итог конкурса (число грантов × сила заявителей) |
| Источник истины | adilet.zan.kz (Типовые правила V1800017650, Правила ЕНТ V1700015173), testcenter.kz | Итоги конкурса; практически — агрегатор univision.kz |
| Значения (конкурс 2025) | 50 общий · 65 нац. вузы · 70 медицина · 75 педагогика и право · 60 с/х · 25/35 сокращённые (после колледжа) | Плавает 60–135+: медицина/IT/право в топ-вузах — 120–135; аграрные/пед. в регионах — близко к пороговому |
| Поле в БД | `threshold` | `passing` |

**Смешение этих двух чисел — грубейшая содержательная ошибка** и самая частая ошибка абитуриента. Ассистент обязан объяснять разницу явно при каждом расчёте.

Дополнительный слой сложности: **с 2024 года национальные вузы Астаны и Алматы (КазНУ, ЕНУ и др.) вправе ставить СВОИ проходные баллы** → появляется срез **вуз × ГОП**. Для остальных вузов проходной — **национальный по ГОП** (одна отсечка на страну). Модель обязана поддерживать оба среза и не смешивать их (см. схему `programs`, §4).

### 2.3. Почему «100% точность» — это НЕ гарантия, а исторические отсечки + источник + год + вероятность

Проходной балл будущего года **принципиально не может быть известен заранее**. Он зависит от:
- (а) числа грантов на ГОП в конкретном году (госзаказ меняется приказом ежегодно);
- (б) числа и силы (баллов ЕНТ) заявителей;
- (в) квот и права нац. вузов ставить свои отсечки.

Поэтому **«точность» продукта = честность о неопределённости**, а не выдуманная гарантия. Правильная формулировка ответа:

> «По данным univision.kz за **2025** год, проходной на грант по ГОП **B057 (ИТ)** в вузе X составил **90** (грантов: 115). Исторический разброс 2023–2025: **[85..95]**. Ваш балл **92** → **высокие шансы** (выше прошлогодней отсечки на 2, в пределах исторического коридора). Это **не гарантия**: отсечка 2026 сформируется по итогам конкурса.»

Три обязательных элемента любой числовой рекомендации: **историческая отсечка + явный источник/год + вероятностная формулировка с интервалом**. Никогда — «ты проходишь» без оговорок.

### 2.4. Профильные предметы → специальности (жёсткая привязка)

Абитуриент выбирает **пару профильных предметов ПОД специальность**, а не наоборот. Пара открывает доступ **только** к закреплённым за ней ГОП. Примеры:

| Пара профильных | Открывает ГОП (примеры) |
|---|---|
| Математика + Информатика | ИТ, информационная безопасность, криптология (B057, B058…) |
| Математика + Физика | Инженерия, механика, энергетика |
| Химия + Биология | Медицина (BM086), фармация (B085)… |
| Всемирная история + Основы права | Юриспруденция (B049)… |
| Биология + География | Педагогика/психология (варьируется) |

Официальный перечень привязки — **adilet V1700015186**. Это **входной фильтр** рекомендателя: по паре профильных отсекаем недоступные ГОП **до** любого расчёта баллов.

### 2.5. Accuracy caveat (обязательная оговорка продукта)

> Каждая запись проходного балла помечается `source_url + year + granularity (нац-по-ГОП | вуз×ГОП) + confidence`. Для данных агрегатора (univision) обязательна **выборочная сверка** с официальным приказом о числе грантов (adilet). Общие объёмы (77 084 гранта на 2025-2026; ~75 371 на 2026-2027) **официальны**; конкретные пер-вуз отсечки — **с агрегатора, требуют проверки**. Историческую отсечку **нельзя** показывать как порог текущего года. На 2026-07-02 свежайшие **подтверждённые** отсечки = **2025** (итоги 2026 публикуются ~август 2026).

Это прямое развитие **ADR-009** (проходные баллы не как факт в MVP → честный отказ). Расширение: теперь мы **можем** давать число, но **только** из структурного стора, с провенансом и как вероятность — не из семантики и не из головы LLM.

### 3.2. Рекомендованный первичный источник для проходных баллов

**Двухслойная стратегия (точность через перекрёстную сверку):**

1. **Ядро проходных (фичи):** `univision.kz` — `/univ/{id}/ball` (вуз×ГОП с числом грантов) + `/grant/passing.html` (нац. срез) + архив по годам. Это **единственный практически доступный** источник, где проходной дан в разрезе И вуза, И ГОП, И с числом грантов. Минус — HTML без API.
2. **Официальное ядро (валидация + цитаты для защиты):** `adilet` (G24HN000193 — объёмы; Типовые правила — пороги) + `testcenter.kz` (процедура, итоги). Ими **сверяем** univision и на них **ссылаемся** в accuracy-обосновании.
3. **Стоимость:** сайты приёмных комиссий (per-вуз). Единого нацреестра цен **нет**.

**Итог:** `univision.kz` = операционный источник фичей (проходной × вуз × ГОП × год); `adilet + testcenter` = слой валидации и официальные ссылки; сайты вузов = стоимость.

### 3.3. План сбора и обновления

```
1) ОБЪЁМЫ ГРАНТОВ (официально, приоритет):
   adilet G24HN000193 (DOCX/HTML) → python-docx / pandas.read_html
   → справочник {код ГОП, наименование, всего, полное, сокращённое, квоты} × год.
   Это ground-truth объёмов (напр. B057 ИТ = 5425).

2) ПОРОГОВЫЕ БАЛЛЫ (официально):
   Типовые правила V1800017650 / V2300033345 + testcenter min-scores
   → {направление → threshold}. Обновляется редко.

3) ПРОХОДНЫЕ БАЛЛЫ (ядро фичей, univision):
   a. Каталог вузов → URL /univ/{id}-{slug}/ball
   b. Скрейп HTML-таблиц (requests + BeautifulSoup; Playwright если JS)
      → {вуз, код ГОП, ГОП, квота, passing, число грантов, год}
   c. /grant/passing.html: проверить Network на скрытый JSON-эндпоинт
      (если есть — скрейпить его напрямую); перебор ГОП × форма × квота
   d. Историч. годы: подтвердить архивные URL / web.archive.org, метка year;
      join по коду ГОП (B### стабильны между годами)

4) РЕЗУЛЬТАТЫ (result.univision.kz): PDF → pdfplumber/camelot; доп. сверка.

5) СТОИМОСТЬ: per-вуз скрейп admissions-сайтов; прайсы часто PDF → pdfplumber;
   нормализовать {вуз, ОП, форма, цена_тг, год}.

6) ВАЛИДАЦИЯ/ХРАНЕНИЕ: связать passing (univision) с объёмами (adilet) по коду ГОП;
   флагить расхождения. Поля записи: source_url, source_type (official|aggregator),
   year, granularity, scraped_at, confidence.
   Бережный краулинг (rate-limit, UA, кэш, robots.txt).
   Пересборка ЕЖЕГОДНО после публикации итогов (~август).
```

### 3.4. Что делаем, если авторитетного машиночитаемого источника нет

Это **реальный кейс**: единого официального машиночитаемого реестра **проходных** баллов вуз×специальность **не существует** (официально публикуются только объёмы по ГОП и пороги). Протокол:

1. **Ручная выверка** значения из агрегатора против официального объёма грантов (adilet) — если число грантов на ГОП совпадает, доверие к строке выше.
2. **Провенанс обязателен:** `source_url`, `source_type=aggregator`, `scraped_at`, `confidence` (снижаем для непроверенных).
3. **Версия/год явно:** `year` в каждой записи; отсутствие свежего года → показываем последний подтверждённый (2025) с оговоркой «данные за прошлый год».
4. **Отказ вместо выдумки:** если по ГОП/вузу нет данных ни в одном слое — **честный отказ** («по этой программе исторических данных нет; ориентируйтесь на пороговый балл N и уточните в приёмной комиссии»), а **не** интерполяция/выдумка. Прямое следствие инварианта §2 (анти-галлюцинация) и ADR-009.

## 4. Архитектура (эволюция фундамента)

### 4.1. КЛЮЧЕВОЕ РЕШЕНИЕ — два разделённых движка

```
                    ┌─────────────────────────────────────┐
                    │  Оркестратор запроса (FastAPI)        │
                    │  резолв tenant_id + маршрутизация     │
                    │  intent: "документ?" | "куда пройду?" │
                    └───────────┬───────────────┬───────────┘
                                │               │
                 intent=doc-QA  │               │  intent=recommend
                                ▼               ▼
        ┌───────────────────────────┐   ┌──────────────────────────────┐
        │  ДВИЖОК A — RAG (§00)      │   │  ДВИЖОК B — РЕКОМЕНДАТЕЛЬ     │
        │  pgvector hybrid dense+FTS │   │  Реляционная таблица programs │
        │  RRF + rerank + confidence │   │  (Postgres) + rules-движок    │
        │  → ответ + цитаты          │   │  → расчёт + вероятность +     │
        │  (регламенты, стоимость,   │   │    источник/год + объяснение  │
        │   сроки, "как перевестись")│   │  ("куда пройду на грант")     │
        └───────────────────────────┘   └──────────────────────────────┘
                    точный текст                 точные числа
```

**Почему разделяем:**

| | Движок A (RAG / vector) | Движок B (структурный стор / rules) |
|---|---|---|
| Данные | Неструктурированный текст (PDF, регламенты) | Структурированные числа (балл, год, число грантов, цена) |
| Тип вопроса | «Как?», «Можно ли?», «Что нужно?» | «Сколько?», «Куда пройду?», «Сравни» |
| Точность чисел | Плохая (семантика теряет id/дату/балл) | **Точная** (SQL, детерминированно) |
| Multi-hop/сравнение | Плоский top-k **не умеет** (риск №15, §00) | **Умеет** (GROUP BY, ORDER BY, JOIN) |
| Объяснимость | Цитата-чанк | **Точная строка-источник** + год + confidence |

Это **прямое применение инсайта docs/02**: структурированные точные данные (id/дата/баллы) держим как **структурный слой**, а **НЕ через семантику**; плоский top-k не умеет multi-hop/сравнения → **структурированный стор точнее графа** для числовых данных.

### 4.2. Почему баллы — это структурный стор + rules, а НЕ GraphRAG / семантика

**Три причины, каждая критична для этого продукта:**

1. **Точность.** «Проходной по B057 в вузе X за 2025» — это **одна ячейка таблицы**. Векторный поиск вернёт *похожие* чанки (риск выдать 90 вместо 92, балл 2024 вместо 2025). SQL-запрос вернёт **ровно то число**. Для числовой рекомендации, где ошибка в 1 балл = неверный совет о судьбе абитуриента, семантическая близость **недопустима**.
2. **Объяснимость.** Rules-движок даёт трассируемое объяснение: «балл 92 ≥ отсечка 90 (2025) → проходит; интервал [85..95]». Каждый шаг проверяем и цитируем. GraphRAG/LLM-over-vector дают *правдоподобный* текст без гарантии, что число не сдвинулось при генерации.
3. **Цитата-источник.** Требование §00 (инвариант «цитаты из метаданных, не из текста модели»). В структурном сторе `source_url + year + confidence` лежат **рядом с числом** как колонки — цитата строится детерминированно, а не «придумывается».

**Где GraphRAG реально полезен, а где избыточен:**

- **Полезен** (будущий rich-mode, ADR-012): цепочки документов — «как перевестись с платного на грант KBTU → какие регламенты → сроки → условия по GPA». Это **multi-hop по неструктурированному тексту**, где связи между документами важны. Community Summaries для обзорных вопросов («расскажи про все виды грантов вуза»).
- **Избыточен / вреден** для баллов: числовая отсечка — это **не граф связей**, это **таблица фактов**. Строить граф «вуз→ГОП→балл→год» поверх того, что идеально ложится в реляционную строку, — усложнение без выигрыша в точности, с потерей детерминизма. **Для баллов граф проигрывает таблице** (инсайт docs/02).

**Вывод:** Движок B = **реляционная таблица + rules**. GraphRAG остаётся будущим расширением **движка A** (текстовый multi-hop), не движка B.

### 4.3. Как LLM работает поверх структурного движка

LLM здесь — **переводчик и объяснитель, не источник чисел**:

```
Пользователь: "балл 92, математика и информатика, хочу в Алматы, IT"
        │
        ▼
[1] LLM: NL → структурный запрос (function-calling / structured output)
        {ent_score: 92, profile: [math, informatics],
         city: "Алматы", ГОП_фильтр: IT-группы (B057/B058)}
        │
        ▼
[2] Rules-движок + SQL по таблице programs (детерминированно):
        - фильтр по threshold (допуск) и паре профильных
        - JOIN с историческими passing по ГОП×вуз×год
        - классификация: проходит / рискованно / не проходит
        │
        ▼
[3] LLM: структурный результат → человеческое объяснение
        + ОБЯЗАТЕЛЬНО подставляет цитаты/год/интервал ИЗ результата,
          НЕ из своей памяти (числа приходят только из шага 2)
```

**Анти-галлюцинация числовых данных (жёсткий инвариант):** LLM **никогда** не генерирует балл. Все числа в ответе — плейсхолдеры, заполняемые из результата SQL. Если стор пуст → LLM выдаёт **шаблон отказа**, не число. Это тот же паттерн, что confidence-gate движка A (§9.1 §00), перенесённый на структурный слой.

### 4.4. Схема данных `programs` (структурный стор, движок B)

Реляционная БД (Postgres — транзакции, JOIN, аналитика для B2B-дашборда). Ядро — таблица `programs` + история отсечек + стоимость:

```sql
-- Справочник ГОП (стабильные коды B### между годами)
CREATE TABLE gop (
    gop_code        TEXT PRIMARY KEY,      -- 'B057'
    gop_name        TEXT NOT NULL,         -- 'Информационные технологии'
    threshold       INT,                   -- пороговый (допуск), из adilet/testcenter
    threshold_src   TEXT,                  -- adilet V1800017650
    profile_subjects JSONB                 -- [['математика','информатика'], ...] допустимые пары
);

-- Вузы (совпадает с tenant_id из §00 для вузов-клиентов;
--       вузы без RAG-подписки существуют как справочные строки)
CREATE TABLE universities (
    univ_id         TEXT PRIMARY KEY,      -- 'kaznu'
    tenant_id       TEXT UNIQUE,           -- NULL если вуз не клиент RAG (только в рекомендателе)
    name            TEXT NOT NULL,
    city            TEXT,
    univ_type       TEXT,                  -- national|private|autonomous
    is_national     BOOLEAN,               -- вправе ставить свои отсечки (2024+)
    admission_track TEXT DEFAULT 'ent'     -- 'ent' | 'autonomous' (NU/KIMEP — свои экзамены)
);

-- Программа = ГОП в конкретном вузе (единица рекомендации)
CREATE TABLE programs (
    program_id      BIGSERIAL PRIMARY KEY,
    univ_id         TEXT REFERENCES universities,
    gop_code        TEXT REFERENCES gop,
    faculty         TEXT,
    tuition_paid_kzt INT,                  -- стоимость платного, тг/год (из сайта вуза)
    tuition_year    INT,
    tuition_src     TEXT,                  -- welcome.kaznu.kz/... (провенанс)
    seats_grant     INT,                   -- число грантов (из adilet, ground truth)
    UNIQUE (univ_id, gop_code)
);

-- ИСТОРИЯ проходных отсечек — сердце рекомендателя
-- Каждая строка = одна отсечка с полным провенансом
CREATE TABLE passing_scores (
    id              BIGSERIAL PRIMARY KEY,
    univ_id         TEXT REFERENCES universities,  -- NULL = национальный срез по ГОП
    gop_code        TEXT REFERENCES gop NOT NULL,
    year            INT NOT NULL,                  -- 2023 | 2024 | 2025
    passing_score   INT NOT NULL,                  -- отсечка последнего грантника
    grants_count    INT,                           -- число грантов в этой строке
    quota_type      TEXT DEFAULT 'general',        -- general|rural|orphan|disabled|... (НЕ смешивать!)
    granularity     TEXT NOT NULL,                 -- 'national_gop' | 'univ_gop'
    source_url      TEXT NOT NULL,
    source_type     TEXT NOT NULL,                 -- 'official' | 'aggregator'
    confidence      TEXT NOT NULL,                 -- high|medium|low
    scraped_at      TIMESTAMPTZ NOT NULL,
    UNIQUE (univ_id, gop_code, year, quota_type, granularity)
);
CREATE INDEX ix_ps_lookup ON passing_scores (gop_code, univ_id, year);
```

**Ключевые свойства схемы:**
- `threshold` (в `gop`) и `passing_score` (в `passing_scores`) — **физически разные колонки в разных таблицах** → смешать невозможно by design (§2.2).
- `granularity` разделяет нац-срез и вуз×ГОП (право нац. вузов с 2024).
- `quota_type` изолирует квотные отсечки (обычно ниже) от общего конкурса — **не смешивать** (риск §2).
- `source_url + year + source_type + confidence + scraped_at` — провенанс **на каждой** записи (§3.4).
- `admission_track='autonomous'` помечает NU/KIMEP — рекомендатель **не** применяет к ним логику ЕНТ-конкурса (§5).

### 4.5. Мультитенант: как вписывается `tenant_id` и кросс-вузовый слой

Тонкий, но важный момент — **у двух движков разная тенантность:**

| | Движок A (RAG) | Движок B (Рекомендатель) |
|---|---|---|
| Тенантность | **Строго per-tenant** (§00): каждый запрос — обязательный `tenant_id`-фильтр в pgvector (в той же Postgres). Документы KBTU не видны из контекста ЕНУ. | **Кросс-вузовый по природе**: «куда пройду» = сравнение по ВСЕМ вузам. Данные о баллах/грантах — **публичные**, не приватные документы вуза. |

Это **не противоречие**, а два разных класса данных:

- **Приватный слой (документы вуза)** → pgvector (Postgres), `tenant_id`-изоляция, инвариант §2 незыблем.
- **Публичный кросс-вузовый слой (баллы, гранты, стоимость)** → Postgres `programs`, **без** tenant-изоляции (данные и так публичны), но `univ_id` связан с `tenant_id` для вузов-клиентов.

**Связка:** `universities.tenant_id` = FK к реестру тенантов §00. Когда вуз становится RAG-клиентом, его `univ_id` получает `tenant_id`, и в UI абитуриента рядом с рекомендацией «пройдёшь в KazNU» появляется кнопка «спросить ассистента KarNU о документах» → движок A с этим `tenant_id`. Вузы **без** подписки живут в рекомендателе как справочные строки (`tenant_id = NULL`) — они всё равно в выдаче (публичные данные), но без RAG-ассистента. **Это и есть бизнес-крючок** (§6): «хотите ассистента и приоритет в выдаче — станьте клиентом».

**Инвариант изоляции §2 не нарушается:** приватные документы по-прежнему за `tenant_id`-фильтром; публичные баллы никогда не были приватными. Единый code path к вектор-стору (§2) сохраняется; **и вектор (движок A, pgvector), и реляционные таблицы (движок B) живут в ОДНОЙ Postgres** — изоляция документов по `tenant_id`, баллы как публичный кросс-вузовый слой (ADR-016).

## 5. Логика рекомендаций

### 5.1. Пошаговый алгоритм

```
ВХОД: {балл ЕНТ, профильные предметы (пара), приоритеты: город/специальность/бюджет}

ШАГ 1 — ФИЛЬТР ДОСТУПА (профиль + порог)
  • по паре профильных → допустимые ГОП (adilet V1700015186)
  • по threshold ГОП → отсечь программы, куда балл НЕ допускает к конкурсу
    (напр. балл 68 → медицина threshold 70 недоступна вообще)
  → выход: множество допустимых {ГОП × вуз}

ШАГ 2 — СОПОСТАВЛЕНИЕ С ИСТОРИЧЕСКИМИ ОТСЕЧКАМИ
  для каждой допустимой программы:
    • достать passing_scores по (gop_code, univ_id) за 2023–2025
    • взять последний год (2025) + интервал [min..max]
    • сравнить балл с отсечкой

ШАГ 3 — КЛАССИФИКАЦИЯ (3 корзины)
    ✅ ПРОХОДИТ НА ГРАНТ:  балл ≥ passing_2025 + запас (напр. ≥ отсечка+3)
    ⚠️  РИСКОВАННО:         балл в коридоре [passing_2025−3 .. passing_2025+3]
                            или ниже max исторического интервала
    ❌ НЕ ПРОХОДИТ:         балл < min исторического интервала

ШАГ 4 — СОРТИРОВКА И СТРАТЕГИЯ ПРИОРИТЕТОВ
  • сортировка: сначала ✅ по желанию (город/специальность), потом ⚠️, потом ❌
  • СИМУЛЯЦИЯ 4 ПРИОРИТЕТОВ: рекомендовать смесь
      приоритет 1–2: амбициозные (⚠️ желанные)
      приоритет 3–4: реалистичный запас (✅ гарантированные)
    предупреждение: "4 недостижимых выбора → рискуешь остаться без гранта"

ШАГ 5 — ЕСЛИ НЕ ХВАТАЕТ (все корзины ❌ по желанным)
  → дерево сценариев (§5.2)
```

### 5.2. Дерево «баллов не хватило» (структурированное, каждый узел с условиями)

```
Баллов не хватило на желанный грант
├── A. ПЛАТНОЕ по бюджету пользователя
│     • фильтр programs.tuition_paid_kzt ≤ бюджет
│     • + перспектива перевода на грант по успеваемости (освободившиеся места)
│     • показать цену + источник (сайт вуза) + год
├── B. ПЕРЕСДАЧА ЕНТ
│     • летом до 2 попыток → выбрать лучший сертификат
│     • оценка: "нужно +N баллов до отсечки B057 — реалистично?"
├── C. НИЖЕ-КОНКУРСНЫЕ ГОП/вузы (тот же профиль)
│     • те же профильные, но ГОП/вуз с отсечкой ≤ балл
│     • напр. IT в региональном вузе вместо топ-Алматы
├── D. ГРАНТЫ АКИМАТОВ / местных бюджетов + вузовские гранты
│     • отдельные конкурсы, меньше конкуренция, часто отработка в регионе
│     • напр. KBTU: 15 грантов Нацбанка 100% + 15 KBTU 50%
├── E. КОЛЛЕДЖ → сокращённая программа
│     • пороги ниже: 25 (общий) / 35 (педагогика)
│     • позже поступление в вуз по сокращёнке
├── F. АВТОНОМНЫЙ ТРЕК (NU / KIMEP)
│     • admission_track='autonomous' → НЕ логика ЕНТ-конкурса
│     • собственные экзамены (NUET, English, интервью), платно
│     • показать как ОТДЕЛЬНУЮ ветку, не через грант-конкурс
└── G. СЛЕДУЮЩИЙ ГОД (подготовка)
```

### 5.3. Как показываем неопределённость и источник

Каждая карточка результата содержит:

```
┌──────────────────────────────────────────────────────────┐
│ ✅ B057 Информационные технологии — КазНУ им. аль-Фараби  │
│                                                            │
│ Проходной на грант 2025: 90  (грантов: 115)                │
│ Исторический коридор 2023–2025: [85 .. 95]                 │
│ Ваш балл: 92 → ВЫСОКИЕ ШАНСЫ (выше отсечки-2025 на +2)     │
│                                                            │
│ ⚠️  Это не гарантия. Отсечка 2026 сформируется по итогам   │
│    конкурса (зависит от числа грантов и силы заявителей).  │
│                                                            │
│ 📎 Источник: univision.kz · год: 2025 · срез: вуз×ГОП      │
│    достоверность: средняя (агрегатор, сверено с adilet)    │
│ 💬 Спросить ассистента КазНУ о документах →                │
└──────────────────────────────────────────────────────────┘
```

Обязательные элементы: **число + год + интервал + вероятностная формулировка + провенанс + оговорка «не гарантия»**.

### 5.4. Анти-галлюцинация для числовых данных

**Жёсткие правила (инвариант продукта, расширение §2 §00):**

1. **Ни один балл в ответе не генерируется LLM.** Все числа — из `passing_scores` / `programs` через SQL. LLM только форматирует.
2. **Нет данных → отказ, не выдумка.** Если по (ГОП, вуз, год) строки нет → «исторических данных по этой программе нет; ориентируйтесь на пороговый балл N, уточните в приёмной комиссии» — **никакой** интерполяции.
3. **Год всегда явно.** Запрещено показывать отсечку без года. Свежайшая подтверждённая = 2025.
4. **threshold ≠ passing.** UI и текст всегда маркируют, какое из двух чисел показано.
5. **Провенанс обязателен.** Нет `source_url` → строка не показывается как факт.
6. **Квоты изолированы.** Квотную отсечку не выдавать за общий конкурс (`quota_type`).

### 6.1. Модели дохода (ориентиры в тенге)

| Модель | Механика | Ориентир цены | Комментарий |
|---|---|---|---|
| **Подписка (тиры)** | Доступ к RAG-ассистенту + профилю + дашборду лидов | **Free / Basic ~150–300 тыс тг/год / Pro ~600 тыс–1.2 млн тг/год / Enterprise ~2–4 млн тг/год** | Основа выручки. Тир = объём лидов + аналитика + брендинг. |
| **Pay-per-lead** | Плата за квалифицированный лид (абитуриент кликнул «узнать/подать», подходящий по баллу) | **~1 500–5 000 тг/лид** (выше для медицины/IT/права) | Понятная вузу метрика: платишь за целевого абитуриента. |
| **Sponsored placement** | Приоритет в выдаче (помечен «реклама»/«партнёр») | **~300–800 тыс тг/сезон** за ГОП-категорию | **Только видимость, НЕ подмена факт-рекомендации** (§6.5). |
| **Аналитика спроса** | Дашборд: сколько абитуриентов с какими баллами искали эту ГОП, конверсии, конкуренты | входит в Pro/Enterprise или **~400–900 тыс тг/год** | Часто **самая ценная** для маркетинга вуза часть. |
| **Виртуальные дни открытых дверей** | Онлайн-презентация/Q&A в платформе для целевых абитуриентов | **~200–500 тыс тг/событие** | Сезонный доп-продукт (весна–лето). |

### 6.2. Cold-start двустороннего рынка (как заводим)

Классическая проблема курицы-яйца решается **однобокой заправкой со стороны спроса на публичных данных:**

```
ФАЗА 0 (до продаж вузам): наполняем СТОРОНУ СПРОСА
  • собираем публичные данные (§3): баллы (univision) + пороги/объёмы (adilet)
    + стоимость (сайты вузов) → рекомендатель работает БЕЗ единого вуза-клиента
  • абитуриент получает ценность сразу (расчёт "куда пройду") на публичных данных
  → ГЕНЕРИРУЕМ ТРАФИК И ЛИДЫ независимо от вузов

ФАЗА 1 (есть трафик): продаём вузам ПРИСУТСТВИЕ и ЛИДЫ
  • "к вам уже приходят N абитуриентов/сезон с баллами X — вот их спрос"
  • claim-your-profile: вуз забирает свой (уже существующий) профиль
  → вуз платит за то, что трафик УЖЕ есть

ФАЗА 2 (вузы внутри): апселл RAG-ассистента
  • "загрузите свои документы → ваш ассистент отвечает абитуриентам 24/7"
  → движок A (§00) как премиум-фича подписки
```

Ключ: **сторона спроса самодостаточна на публичных данных** — не ждём вузов, чтобы дать ценность абитуриенту. Трафик = актив для продажи вузам.

### 6.3. Как заставить вузы приносить документы и платить

- **Claim-your-profile:** профиль вуза **уже существует** (заполнен публичными данными). Вуз его «забирает», верифицируется → бесплатно правит базовую инфу. Психология: страница уже работает и собирает лиды **без** них → FOMO.
- **Freemium:** бесплатно — базовый профиль + N лидов/мес. Платно — безлимит лидов + RAG-ассистент + аналитика + брендинг.
- **Дашборд лидов** как крючок: вуз **видит** входящий спрос (баллы, ГОП, город) → хочет больше → апгрейд.
- **Self-serve загрузка документов:** вуз сам приносит PDF → наш ingestion (§00 §7, Typer-CLI, новый YAML **без кода** — уже заложено в §00 «второй вуз без кода») → ассистент оживает за часы. Низкий порог = вуз делает работу сам.

### 6.4. ЛПР в вузе, цикл продаж, пилот

- **ЛПР:** проректор по развитию/академическим вопросам (стратегия, бюджет) + **начальник приёмной комиссии** (операционный владелец боли «поток абитуриентов») + отдел маркетинга (спрос/бренд). Приёмная комиссия — **входная точка** (у них острая сезонная боль).
- **Цикл продаж:** длинный, привязан к бюджетному году вуза; решение — коллегиальное. Заходить **осенью-зимой** (планирование бюджета на след. приёмную кампанию), запускать **к весне-лету**.
- **Пилот:** 1 «якорный» вуз (в проекте уже **KBTU** — эталон §00, документы верифицированы) + 1-2 из стартового набора (КазНУ, ЕНУ, Satbayev, MNU, AITU, SDU, KIMEP). Пилот = бесплатный сезон в обмен на кейс и данные. Доказываем лидами → конвертируем в подписку.

### 6.5. ЭТИКА (нерушимый принцип продукта)

> **Фактическая грант-рекомендация НЕ продаётся.** Расчёт «пройдёшь / не пройдёшь на грант» строится **только** на данных и правилах (§5), одинаково для всех вузов, **вне зависимости от того, платит вуз или нет**. Деньги вуза покупают **исключительно видимость и промо** (sponsored placement, приоритет в выдаче, брендинг, виртуальный день открытых дверей) — и **всегда чётко маркируются** («партнёр» / «реклама»). Платный вуз **не** может подняться в факт-рекомендации выше того, куда абитуриент реально проходит по баллу. Нарушение = смерть доверия = смерть продукта. Это совпадает с целью «defendable»: продукт защитим именно потому, что честен.

### 6.6. Метрики бизнеса

- **Спрос:** MAU/сезонные визиты, число расчётов рекомендаций, доля завершённых расчётов, retention родитель↔абитуриент.
- **Двусторонность:** число вузов-профилей (claimed vs unclaimed), конверсия claim→платный, лиды/вуз/сезон, cost-per-lead.
- **Выручка:** ARR по тирам, ARPU вуза, доля sponsored vs subscription, churn вузов после сезона.
- **Качество (защита доверия):** доля рекомендаций с полным провенансом (цель 100%), число жалоб на неверный балл, свежесть данных (лаг от публикации итогов до обновления стора).

## 7. Дорожная карта расширения и риски

### 7.1. Как расширение ложится на этапы 1–5 (§00 §15)

Расширение — **отдельный трек поверх** MVP §00, не ломает его DoD. Привязка:

| Этап §00 | Что добавляет расширение |
|---|---|
| **Этап 1 (ingestion)** | Тот же CLI/YAML — **второй+ вуз без кода** (уже в §00). Плюс: скрейперы публичных данных (adilet DOCX, univision HTML, PDF-прайсы вузов) → **не в вектор-таблицу `chunks`, а в реляционные `programs`** (та же Postgres). |
| **Этап 2 (retrieval)** | Вектор-стор движка A (pgvector) — тот же Postgres. **Новое:** реляционные схемы `programs/passing_scores/gop` в той же БД, ETL-валидация (сверка univision↔adilet). |
| **Этап 3 (LLM/guard)** | Расширить: NL→структурный запрос (function-calling), rules-движок, анти-галлюцинация чисел (§5.4). Confidence-gate распространить на пустой структурный результат. |
| **Этап 4 (UI)** | Новый экран рекомендателя (ввод балл+профиль → 3 корзины + дерево «не хватило»). Карточки с провенансом (§5.3). B2B: claim-профиль, дашборд лидов. |
| **Этап 5 (eval)** | Golden set для рекомендателя: пары (вход → ожидаемая корзина/вуз) на исторических данных; тест «threshold≠passing не спутаны»; тест «нет данных → отказ, не выдумка»; свежесть данных как метрика. |

**Новый этап 6 (пост-защита, B2B):** биллинг/тиры per-tenant, claim-flow, sponsored-placement с маркировкой, аналитический дашборд, ежегодный ре-скрейп (~август).

### 7.2. Новые риски и митигации

| # | Риск | Митигация |
|---|---|---|
| R1 | **Устаревшие баллы** (данные прошлого года выданы за текущий) | `year` обязателен в каждой записи; UI всегда показывает год; ежегодный ре-скрейп после итогов (~август); метрика свежести на дашборде. |
| R2 | **Юр. ответственность за неверную рекомендацию** (абитуриент не поступил, винит нас) | Продукт позиционируется как **справочно-аналитический**, не гарантия (§2.3, §5.3). Явный дисклеймер «не гарантия, отсечка формируется постфактум» в каждой карточке. Провенанс = мы показали источник, не выдумали. Согласие с условиями при входе. |
| R3 | **threshold/passing спутаны** (грубая содержательная ошибка) | Физически разные колонки в разных таблицах (§4.4); UI-маркировка; unit-тест в eval; невозможно by design. |
| R4 | **Доверие подорвано выдуманным баллом** | Инвариант §5.4: балл только из стора, нет данных → отказ. Ни одна цифра не из LLM. |
| R5 | **Спонсорство искажает факт-рекомендацию** (этический провал) | §6.5: факт-рекомендация не продаётся; sponsored только видимость + маркировка. Тех. разделение: rules-движок не знает о статусе оплаты вуза. |
| R6 | **GDPR / ЗоПД РК (перс. данные абитуриентов)** — балл ЕНТ, ИИН, предпочтения | Не хранить ИИН без нужды; минимизация данных; согласие на обработку; данные о спросе для вузов — **агрегированные/обезличенные** (не «Иван 92 балла», а «N абитуриентов 90–95»). Хостинг перс. данных резидентов РК — с учётом требований локализации ЗоПД РК. |
| R7 | **Гранулярность: нет «балла по специальности», только по ГОП** | UX проговаривает: «конкурс идёт по группе программ B057, не по отдельной специальности» (§2.1). Не обещать точность уровня специальности на этапе гранта. |
| R8 | **Агрегатор (univision) ошибся/задержал данные** | Обязательная сверка с adilet (объёмы грантов) по коду ГОП; `confidence` понижается для непроверенного; расхождения флагятся ETL. |
| R9 | **Автономный трек (NU/KIMEP) объяснён через грант-логику** → неверный совет | `admission_track='autonomous'` → отдельная ветка (§5.2 F); рекомендатель не применяет к ним ЕНТ-конкурс. |
| R10 | **Нац. вузы с 2024 ставят свои отсечки** — смешение с нац. срезом искажает оценку | `granularity` (national_gop vs univ_gop) разделяет срезы; для топ-вузов брать univ_gop, для остальных national_gop. |

### Итоговое резюме для защиты

- **Что нового:** над RAG-ассистентом одного вуза (§00) надстроена **двусторонняя платформа** с **вторым, структурным движком** рекомендаций «куда пройду на грант».
- **Главное архитектурное решение:** два разделённых движка — **A (RAG/vector)** для документов и **B (Postgres + rules)** для чисел. Баллы — **структурный стор, не семантика и не граф** (точность + объяснимость + цитата-источник; прямое следствие инсайта docs/02).
- **Главный содержательный дифференциатор:** честное разделение **пороговый vs проходной** балл + вероятность с интервалом и провенансом вместо ложной «гарантии».
- **Бизнес:** cold-start решается заправкой стороны спроса на публичных данных → трафик → продажа вузам лидов и присутствия; **факт-рекомендация неприкосновенна и не продаётся** (этика = защищаемость).

## 1. Проблема и цель продукта

**Проблема.** Абитуриент РК после ЕНТ не понимает: (а) проходит ли он на грант и куда (путает пороговый балл с проходным); (б) как расставить 4 приоритета заявления; (в) что делать, если баллов не хватило. Существующие агрегаторы дают таблицы без методики, гарантий-дисклеймеров и сценария «не прошёл».

**Цель MVP.** Публичный бесплатный веб-инструмент: балл + профильные предметы → честный расклад «✅ прохожу / ⚠️ на грани / ❌ не хватает» по историческим отсечкам с провенансом, и дерево действий «если не хватило». Бизнес-цель — валидация спроса (метрики §18) как актив для B2B-фазы.

## 2. Пользователи и покупатели

| Роль | Кто | Ценность |
|---|---|---|
| Пользователь-1 | Абитуриент (11 кл. / после колледжа), пик боли июль-август | Расчёт шансов + план действий |
| Пользователь-2 | Родитель | Понятное «куда реально проходит ребёнок и сколько стоит платное» |
| Мультипликатор | Репетитор/учитель (тёплый канал владельца) | Рабочий калькулятор для учеников |
| Покупатель (не MVP) | Вуз (фаза B2B при выполнении условия перехода docs/02 §2) | Лиды, аналитика спроса, ассистент |

## 3. Выбранная модель продукта

B2C-инструмент на **движке B** (структурный стор + rules, БЕЗ LLM в контуре ответа). Модуль A (RAG по документам) — в консервации (§9). Деньги в 2026 = 0 сознательно (docs/02 §2, трейд-офф зафиксирован).

## 4. Scope MVP

1. Веб-инструмент (эволюция `poc/grant-recommender/pitch/`): расчёт, 3 корзины, дерево «не хватило», провенанс. Статика, расчёт на клиенте.
2. Пайплайн данных «одной командой»: `scrape → validate → build_db → build_pitch → deploy` (§8).
3. Выборочная сверка с adilet + бейджи расхождений (§13).
4. Событийная аналитика + обратная связь (§16).
5. Юр-минимум: условия использования, дисклеймеры (§17).
6. Дистрибуция-операции (docs/02 §4): репетиторы (тёплые), Telegram-посев, аутрич ≥10 вузам.

## 5. Что исключено из MVP (замороженный список)

LLM-чат и любая генерация текста моделью; аккаунты/регистрация; оплата; серверный бэкенд как обязательное звено; admin-панель вузов; мобильное приложение; квоты в рекомендациях (до фикса 177 дублей скрейпера); GraphRAG/reranker/Langfuse; Postgres-миграция; новые документы вузов для модуля A. Любое добавление — только через проверку feature-creep (какую проблему решает / влияет ли на условие перехода / что откладываем взамен) и запись в ADR.

## 6. Пользовательские сценарии (acceptance-сценарии)

- **US-1 «Прохожу?»:** ввожу 100, «математика+информатика» → ≤2 сек вижу 3 корзины; в ✅ есть программы с отсечкой ≤97; каждая карточка содержит: код ГОП, название, вуз, город, отсечка+год, число грантов, порог допуска, мой gap, источник.
- **US-2 «На грани»:** балл = отсечка±3 → программа в ⚠️ с текстом «на грани прошлогодней отсечки, не гарантия».
- **US-3 «Не хватило»:** балл 55, «химия+биология», бюджет 2 млн → блок сценариев: платное в бюджете (с ценами и источником), пересдача (дефицит баллов до ближайшей отсечки), ниже-конкурсные, гранты акиматов (статичная справка), колледж (пороги 25/35), автономный трек NU/KIMEP, следующий год.
- **US-4 «Ниже порога»:** балл 45 → программы с порогом 50+ помечены «ниже порога допуска — к конкурсу не допускают», без ложной надежды.
- **US-5 «Родитель с телефона»:** на экране 360px все сценарии US-1..4 работают без горизонтального скролла.
- **US-6 «Скептик»:** на любой цифре вижу год и источник; на странице — «как это работает» с честным объяснением порог≠проходной и «не гарантия».

## 7. Функциональные требования

| ID | Требование | Критерий приёмки (измеримый) |
|---|---|---|
| FR-1 | Ввод: балл 30–140 (слайдер+число), пара профильных (≥5 пар MVP), опц. город, опц. бюджет платного | Невалидный ввод невозможен UI-контролами; смена любого поля пересчитывает ≤2 сек |
| FR-2 | Классификация: `blocked` (балл<порог) / `fail` / `risk` (±3 от отсечки) / `pass` (≥отсечка+3) | Юнит-таблица граничных случаев: 8 кейсов (порог, порог-1, отсечка-4/-3/0/+2/+3/+4) дают ожидаемые корзины |
| FR-3 | Карточка результата: ГОП-код, название, вуз, город, `passing+год`, `grants_count`, `threshold`, gap, источник | 100% карточек содержат все 9 полей; поле без данных не рендерится как пустое/`undefined` |
| FR-4 | Сортировка: pass по убыванию отсечки; fail по близости к баллу; лимиты «ещё N» | Проверка на 3 контрольных запросах |
| FR-5 | Дерево «не хватило» — только когда pass+risk=0; платное фильтруется по бюджету, сортировка по цене, с источником цены | US-3 проходит; при пустой tuition-базе ветка платного показывает честное «нет данных о ценах», не пустоту |
| FR-6 | Числа ТОЛЬКО из данных: ни одна цифра не «зашита» в JS-логике вне `DATA` | grep по бандлу: баллы/цены встречаются только в `const DATA` |
| FR-7 | Профиль-карта: 5 пар с явной пометкой «покрытие частично; канон — приказ V1700015186» (полная карта — P2) | Пометка видна в UI при выборе профиля |
| FR-8 | Отказ вместо выдумки: нет данных по (ГОП×вуз) → программа не показывается; нет данных вообще → «данных нет, ориентир — порог N» | Ни один сценарий не рендерит расчёт без строки данных |

## 9. Модуль A (RAG по документам) — КОНСЕРВАЦИЯ

Чанкинг/таблицы/метаданные/гибридный поиск — контракт зафиксирован в foundation v1.4 (§7, §8, ADR-018) и НЕ разрабатывается в MVP. Обязательства консервации: (а) `tests/test_tenant_isolation.py` остаётся в CI-прогоне и зелёным; (б) код ingestion/retrieval/providers не удаляется и не рефакторится «попутно»; (в) любые изменения — только по задаче B2B-фазы. Расконсервация — по условию перехода docs/02 §2.

## 10. Поиск и фильтрация (в MVP — клиентские)

Фильтры инструмента: профиль (обязателен), город (опц.), бюджет (опц.). Вся фильтрация — по полям `DATA` на клиенте; серверного поиска в MVP нет. Порог допуска считается как max(база 50, нац.вуз 65, ключевые правила 70/75) — как в `thresholds.json`, с пометкой «упрощённые статутные пороги».

## 11. Генерация ответа и guardrails

**LLM в контуре ответа НЕТ** (главный guardrail MVP). Все тексты — шаблоны с подстановкой чисел из данных. Правила (наследуют §5.4 docs/03-strategy): число без года не показывается; порог и проходной никогда не смешиваются в одной подписи; квотные отсечки не используются; «нет данных → отказ» (FR-8). Появление любой LLM-фичи = выход из MVP через ADR.

## 12. Citations и требования к источникам

Каждая цифра несёт: источник (домен), год, дату сбора (в подвале), тип источника (агрегатор/официальный). Бейдж «⚠️ расходится с приказом» при DR-3-расхождении. Запрещено: слово «проверено»/«сверено» без фактически выполненной сверки (урок P0-8).

## 13. Работа с историческими проходными баллами (ядро честности)

| ID | Правило |
|---|---|
| HS-1 | Проходной = **исторический факт года N**, показывается только с годом; прогнозов «на 2027» продукт не делает |
| HS-2 | Пороговый (допуск, известен заранее) и проходной (итог конкурса, постфактум) — раздельные поля, раздельные подписи в UI |
| HS-3 | Формулировки вероятностные: «выше отсечки-2026 на +5 — высокие шансы», никогда «вы поступите» |
| HS-4 | Дисклеймер «не гарантия; отсечка следующего года формируется конкурсом» — в каждой выдаче, не мелким шрифтом в подвале |
| HS-5 | При наличии ≥2 лет данных — интервал [min..max] по годам; при 1 годе — только год с пометкой |
| HS-6 | Квотные отсечки (rural/disability/…) в расчёте НЕ используются до фикса дублей; в UI упоминание «квоты — уточняйте отдельно» |

## 14. Мультиуниверситетская модель данных

Действующая схема (SQLite, `build_db.py`) сохраняется: `universities` (87) → `passing_scores` (metric=passing|threshold, quota_type, year, провенанс) → `tuition`. Расширения DR-3: `validation` (гоп, год, adilet_total, univision_total, verdict). **Жёсткое разделение доменов данных:** официальные документы вуза (chunks, модуль A) ≠ исторические баллы (passing_scores) ≠ справочная информация (статичные тексты сценариев) — никогда не смешиваются в одном сторе/ответе; `universities.univ_id` — единственный общий ключ (tenant-связка для B2B-фазы).

## 15. API и интерфейс

**MVP: интерфейс = статический сайт** (один html + счётчик), API не деплоится. FastAPI POC (`api/main.py`) сохраняется как dev-инструмент и заготовка B2B (не входит в критерии приёмки MVP). Требования UI: RU-язык; заголовок-ценность («Куда я прохожу на грант — честно»); блок «как это работает»; версия данных видна; Lighthouse mobile ≥ 80 по Performance/Accessibility — проверить один раз перед запуском.

| AN-3 | Дистрибуционные метки: `?src=` (tg/tutor/uni) в ссылках посева | Разрез по каналам виден в счётчике |

## 17. Безопасность и приватность

Расчёт на клиенте; балл/профиль **не передаются на сервер** (кроме анонимных событий счётчика без значений балла — проверить payload); ИИН не запрашивается нигде; страница «Условия»: справочный сервис, не оферта, не гарантия; ЗоПД РК: перс.данные не собираются → без согласий, но с честным уведомлением об анонимной статистике. Секреты в коде запрещены (наследие P0, git-hook по желанию P2).

## 18. Метрики качества

**Данные:** ≥95% совпадение объёмов грантов с adilet по сверенным ГОП; 0 строк без провенанса; свежесть — итоги-2026 в проде ≤14 дней после публикации.
**Продукт:** метрики условия перехода и kill-criteria — по docs/02 §2 (окно 01.08–31.10.2026; ≥1000 расчётов/завершённость ≥40% ↔ kill <200, решение до 15.11.2026).
**Регресс:** `pytest tests -q` зелёный на каждом коммите (изоляция тенантов + POC-смоук + новые тесты FR-2/DR-5).

## 19. Критерии приёмки MVP (launch-checklist)

1. ☐ DR-1..DR-4 выполнены; августовский цикл прогнан на данных 2025 (репетиция).
2. ☐ `validation_report.json` существует; расхождения либо 0, либо помечены бейджами в UI.
3. ☐ US-1..US-6 проходят вручную; FR-2 покрыт юнит-тестом; `pytest` зелёный.
4. ☐ Сайт задеплоен на домен (GitHub/Cloudflare Pages), открывается с мобильного (360px без h-scroll).
5. ☐ AN-1..AN-3 работают (событие видно в счётчике с меткой канала).
6. ☐ Страница условий + дисклеймеры HS-4 на месте.
7. ☐ Посев подготовлен: список чатов, сообщение-шаблон, договорённость с ≥2 репетиторами, черновик писем вузам (≥10 адресов).
8. ☐ Git: всё закоммичено; тег `mvp-launch`.

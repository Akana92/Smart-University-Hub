## 2. Целевая модель данных модуля A (B2B-фаза; сейчас — только контракт)

Требуемая иерархия и её маппинг на текущую реализацию:

| Целевая сущность | Сейчас (факт, консервация) | Миграция в B2B-фазе |
|---|---|---|
| **University** | `tenant_id` (строка в `configs/*.yaml`) | Таблица `universities` — общая с движком B (`univ_id`↔`tenant_id` уже связаны в schema_postgres.sql) |
| **Knowledge Base** | Неявно = папка `data/<tenant>/` | Явная сущность `kb` (вуз может иметь несколько: приёмная/студофис) |
| **Document** | `source` (имя PDF) в чанках + запись в `configs/*.yaml` (category, doc_type, standard_code) | Таблица `documents` (id, kb_id, title, category, doc_type, url) |
| **Document Version** | `doc_version` + `file_hash` + `fetch_timestamp` в каждом чанке (download_manifest.json) | Таблица `document_versions` (doc_id, version, hash, fetched_at); чанки ссылаются на version_id — решает риск content drift (риск №16 foundation) |
| **Page / Section** | `page_number`, `section_title`, `heading_path` в чанке | Остаются полями чанка (нормализация страниц не нужна — overkill) |
| **Chunk** | строка `chunks.jsonl` → таблица `chunks` (SQLite/pgvector) | Та же схема §6.1 foundation; `chunk_id` пересчитывается при переиндексации (риск №13 — процедура `--reset-source`) |
| **Embedding** | колонка `embedding` рядом с чанком (384 демо) | `vector(3072)` pgvector; смена модели = миграция колонки + переиндексация (§2.10) |

## 3. Модель исторических баллов (движок B) — НЕ смешивается с документами

Действующая схема сохраняется как целевая: `universities` → `passing_scores` (metric=passing|threshold · quota_type · year · полный провенанс) → `tuition` → `validation` (новая, DR-3). **Инвариант разделения доменов:** RAG-чанки (официальные документы) ≠ исторические баллы ≠ справочные тексты сценариев; единственный общий ключ — `univ_id`. Запрещено: чанкать таблицы баллов в вектор-стор; выдавать числа движка B через генерацию модуля A.

## 4. Контекст запроса (контракт для любой будущей API/маршрутизации)

Каждый запрос B2B-фазы обязан несёт явный контекст (в MVP он вырожден — выбирается пользователем в UI):

```json
{ "university": "kbtu | null(=все, только для движка B)",
  "user_type": "абитуриент | студент | сотрудник",
  "data_type": "official_docs | historical_scores | reference" }
```

Маршрутизация: `historical_scores` → движок B (SQL, только structured store); `official_docs` → модуль A (RAG, обязательный tenant-фильтр §2.4); `reference` → статичные тексты. `user_type` задаёт фильтр `category` (абитуриент → admission_rules) и тон дисклеймеров. Наивный regex-роутер POC (`/v1/ask`) заменяется этим контрактом в B2B-фазе.

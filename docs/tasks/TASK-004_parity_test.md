# TASK-004 — Parity-тест движков расчёта (JS ↔ Python)

**Цель.** Продакшен-расчёт выполняет **JS в `grant-navigator.html`**, а юнит-логика существует и в Python (`recommend.py`). Логика задублирована (маржа `MARGIN=3` ↔ `const M=3`, `classify`, статутные пороги). Без parity-теста правка одного движка молча разъедется со вторым — это главный способ незаметно сломать честность расчёта.

**Связанный пункт ТЗ:** FR-2 (docs/03_ §7, включительные границы); арх. A4 (docs/04 §5).

**Контекст.**
- Python: `poc/grant-recommender/recommend.py` — `classify(score, passing)` (строки ~57-62), `statutory_threshold(is_national, gop_name)` (~47-55), `MARGIN = 3`.
- JS: `poc/grant-recommender/pitch/index.template.html` — функции `classify`, `threshold`, `const M = 3` внутри `<script>`; используют `DATA.thresholds`.
- Node.js установлен (проверено ранее: `node --check` работал). Подход: тест-раннер извлекает `<script>` из **шаблона** (не из собранного html — тестируем исходник логики), готовит фикстуру `DATA.thresholds` = содержимому `config/thresholds.json`, исполняет функции через `node -e` / временный .mjs и сравнивает с Python.
- **Спек — источник истины** (FR-2, включительные границы): `pass` ⇔ score ≥ passing+3; `risk` ⇔ passing−3 ≤ score < passing+3; `fail` ⇔ score < passing−3; `blocked` ⇔ score < threshold. Если какой-то движок расходится со спеком — чинится ДВИЖОК (минимальным дифом), с явным описанием в отчёте задачи; «подгонка теста под код» запрещена.

**8 граничных кейсов (обязательная таблица):** для passing=90, threshold=65: score = 65 (=порог → допущен), 64 (порог−1 → blocked), 86 (−4 → fail), 87 (−3 → risk), 90 (0 → risk), 92 (+2 → risk), 93 (+3 → pass), 94 (+4 → pass). Плюс 2 кейса threshold-логики: is_national=1 → max(50,65); gop_name содержащий «педагог» → 75.

**Границы.** Только тест + (при расхождении) минимальный фикс движка-нарушителя. UI/вёрстку не трогать.

**Запрещено менять:** значение маржи (=3) и семантику корзин без ADR; шаблон за пределами исправления найденного расхождения; консервацию §9 ТЗ; P2/P3.

**Файлы можно менять/создавать:** `tests/test_engine_parity.py` (новый), `tests/fixtures/` (при необходимости), при доказанном расхождении — `recommend.py` ИЛИ `index.template.html` (одна из, минимальный диф) + пересборка артефакта через TASK-001-скрипт.

**Ожидаемый результат.** `pytest tests/test_engine_parity.py -q` — зелёный: 8+2 кейсов × оба движка идентичны и соответствуют FR-2.

**Критерии приёмки.**
1. Тест реально исполняет ОБА движка (node subprocess + import recommend), не «дублирует таблицу руками».
2. Тест читает JS из `index.template.html` (исходник), а не из собранного файла.
3. При отсутствии node в системе — тест даёт skip с внятным сообщением (не fail), и это отражено в отчёте.

**Definition of Done.** Критерии 1–3; весь `pytest tests -q` зелёный; если было расхождение — оно описано в коммите; коммит `TASK-004: ...`.

**Как проверить.** Запустить тест; временно испортить `M=3→4` в локальной копии шаблона → тест обязан упасть (проверка чувствительности, вернуть обратно).
